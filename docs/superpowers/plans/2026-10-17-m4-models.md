# M4 "3D models and the Ocarina camera" Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An Ocarina-style camera with camera-relative movement, an animated 3D player character (per-race size/colours, body choice, preview), and 3D models for buildings, trees, gates, wells, signs, and walls, with picture cards as the fallback.

**Architecture:** Pure, tested logic in the `maccrossfire` lib: `camera.rs` (directions, swing, pull-in), `models.rs` (mapping file), `walls.rs` (joins from neighbours), `races.rs` (size/colour table, picture → race), `anim.rs` (animation state). Bevy code in `world.rs` (+ new `characters3d.rs`, `buildings.rs`) spawns glTF scenes. Assets: CC0 files under `assets/models/` with licence texts, chosen from free tiers.

**Tech Stack:** Rust stable, Bevy 0.20 (glTF scenes, `AnimationPlayer`/`AnimationGraph`), bevy_egui 0.43; Python 3 (stdlib) only for a glTF inspection script.

**Spec:** `docs/superpowers/specs/2026-10-17-m4-models-design.md`

## Global Constraints

- Assets: CC0 or own work only; free tiers only (owner). Missing piece/animation → nearest substitute, recorded in `assets/models/MISSING.md` with the paid pack that has it.
- No glTF extensions Bevy 0.20 cannot load (Draco, meshopt, `KHR_mesh_quantization`, `EXT_mesh_gpu_instancing`).
- 1 tile = 1 world unit; map x = +X, map y = +Z (north = −Z), as in M1.
- A model that fails to load or has no mapping → the M1 picture card, never nothing.
- Movement still sends Crossfire's 8 directions; the M2 tap/hold rules (one tap = one step) stay.
- Keys: C = camera behind (World mode only). Other keys unchanged.
- Wall joins are computed from neighbouring wall squares in the view (not from picture names).

## Review Focus

1. **A model file missing, corrupt, or slow to load.** Expected: the card shows until the model is ready; a failed load keeps the card and logs once. Test in Task 6 (fallback rule).
2. **A wall at the edge of the view (neighbours unknown).** Expected: treated as "no wall" on that side; it re-joins when the neighbour arrives. Test in Task 4.
3. **The camera between the player and a building/wall corner, or the player inside a doorway.** Expected: the camera pulls in; it never ends inside geometry or at zero distance. Test in Task 1 (pull-in).
4. **Holding a key while the camera swings.** Expected: the compass direction chosen at key-down is kept until release. Test in Task 1.
5. **Unknown race or unknown player picture (other servers).** Expected: default human size and colours. Test in Task 5.

### Task 1: Camera rules (`camera.rs`, pure)

**Interfaces — Produces:**
- `pub type Heading = u8;` (0..8, 45° steps; 0 = camera looking north, 2 = looking east).
- `pub fn screen_dir(up: bool, down: bool, left: bool, right: bool) -> Option<(i8, i8)>` (screen x right, y down; opposites cancel).
- `pub fn compass(screen: (i8, i8), heading: Heading) -> &'static str` — rotate the screen direction by `heading` and return `"north"` … `"northwest"`.
- `pub fn heading_of(dir: u8 /* 1..8 Crossfire */) -> Heading`.
- `pub fn swing(heading: Heading, facing: u8, screen: (i8, i8)) -> Heading` — one step toward `heading_of(facing)` only when `screen.1 < 0` (forward or diagonal forward); else unchanged. Called at most once per `SWING_SECS = 1.0`.
- `pub fn pull_in(distance: f32, blocked: impl Fn(f32) -> bool) -> f32` — `blocked(d)` says whether the camera at distance `d` (along its line) is inside or behind a solid tile; returns the largest `d ≤ distance` in 0.25 steps not blocked, at least `MIN_DISTANCE = 1.5`.

- [ ] **Step 1: Failing tests:** `screen_dirs_and_cancel`; `compass_all_headings` (up at heading 0 → north, at 2 → east, at 4 → south; right at 0 → east; up-left at 6 → southwest… a table of 8×8); `heading_of_round_trip`; `swing_only_when_walking_forward`; `swing_one_step_toward_facing` (shortest way round, 7→0 wraps); `pull_in_finds_clear_spot`; `pull_in_never_below_min`.
- [ ] **Step 2–4:** `cargo test -p maccrossfire camera` → FAIL → implement → PASS.
- [ ] **Step 5: Commit** `feat: camera rules`.

### Task 2: Ocarina camera in the game

**Files:** `world.rs` (camera rig, cards face camera), `input.rs` (camera-relative moves, key-down heading lock, C), `modes.rs` (+ `KeyName::C`, `Act::CameraBehind` in World), `main.rs`.

- Rig: resource `CameraHeading { heading: Heading, shown_yaw: f32 }`; yaw eases toward `heading × 45°`; pitch about 20° above horizontal; default distance 6, zoom 3–12; target = player position + 1.2 up.
- `send_moves`: on key-down, store `(screen_dir, heading)`; while held, keep that compass direction (`compass(screen, locked_heading)`); release clears it. Facing (M2) is set from the compass direction.
- Swing: every `SWING_SECS` while a move is sent, `heading = swing(heading, facing, screen)`.
- C → `heading = heading_of(facing)`.
- Pull-in: `blocked(d)` samples the tile under the camera position at distance `d`; blocked if that tile has a wall/building model (from Task 6's solid set; until then, M1 wall blocks).
- Cards: rotate each frame to face the camera's yaw (y-axis billboard).

- [ ] **Step 2: Implement.**
- [ ] **Step 3: Verify by screenshot:** start (heading 0) and after scripted `right, right, right` + C (camera behind facing east). Warn the owner before sending keys.
- [ ] **Step 4: Commit** `feat: Ocarina camera and camera-relative movement`.
